## Context

`APP_VERSION` is baked into the client bundle at build time via Bun's `define` in `build-client.ts`. The project already has a `pwa-manifest` spec, placing it on the PWA path. No service worker currently exists.

The browser's native SW update lifecycle handles version detection without polling: when the SW file changes on the server, the browser detects it on the next navigation and fires `updatefound`. This is the web standard for this use case.

## Goals / Non-Goals

**Goals:**
- Detect when a new version has been deployed using the Service Worker update lifecycle
- Prompt the user with a dismissible bottom banner (Refresh / Dismiss)
- Dismiss is session-only (reappears after page reload if SW is still waiting)

**Non-Goals:**
- Asset caching or offline support (the SW is minimal — update detection only)
- Auto-reload without user consent
- Polling of any kind

## Decisions

### Service Worker over polling

The browser detects SW file changes by byte-comparing `/sw.js` on each navigation. When changed, it installs the new SW and fires `updatefound`. No extra requests, no timers, no server endpoint needed. This is the correct tool for the job.

### SW file updated by build script

`build-client.ts` writes `public/sw.js` with the current version embedded as a JS constant. This ensures the file changes on every version bump, reliably triggering the browser's update detection:

```js
// public/sw.js (generated by build)
// HowCanI v3.0.44
self.addEventListener('install', () => { /* do not skipWaiting */ });
self.addEventListener('activate', (e) => e.waitUntil(clients.claim()));
self.addEventListener('message', (e) => {
  if (e.data === 'SKIP_WAITING') self.skipWaiting();
});
```

In dev mode, the SW file is **not** written and **not** registered — no banner during development.

### No `skipWaiting()` on install

The new SW waits until the user explicitly clicks "Refresh". The Refresh button sends `SKIP_WAITING` to the waiting SW, then reloads on `controllerchange`. This prevents involuntary page reloads.

### Registration + update detection pattern

```ts
const reg = await navigator.serviceWorker.register('/sw.js');

// Already waiting (e.g., tab was open when deploy happened)
if (reg.waiting) updateAvailable = true;

// New SW installed while tab is open
reg.addEventListener('updatefound', () => {
  const sw = reg.installing;
  sw.addEventListener('statechange', () => {
    if (sw.state === 'installed' && navigator.serviceWorker.controller) {
      updateAvailable = true;
    }
  });
});

// On refresh: trigger new SW to activate, then reload
function refresh() {
  reg.waiting?.postMessage('SKIP_WAITING');
  navigator.serviceWorker.addEventListener('controllerchange', () => {
    window.location.reload();
  }, { once: true });
}
```

### Banner placement

Bottom of the page (above the footer). Non-intrusive — does not block content.

## Risks / Trade-offs

- **First deploy**: On the very first deploy after this feature ships, all existing users have no SW registered. The browser registers the SW fresh — `updatefound` fires but `navigator.serviceWorker.controller` is null (no previous SW), so the banner does not appear. This is correct behaviour: the first registration is not an update.
- **HTTPS requirement**: Service workers require HTTPS in production. The app is already served over HTTPS.
- **Dev mode**: SW registration is skipped in dev to prevent interference with hot reload.

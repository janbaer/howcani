# Code Review Guidelines

## Review Checklist

**Code Quality:**
- Clean separation of concerns?
- Proper error handling?
- Type safety (if applicable)?
- DRY principle followed?
- Edge cases handled?

**Architecture:**
- Sound design decisions?
- Scalability considerations?
- Performance implications?
- Security concerns?

**Testing:**
- Tests actually test logic (not mocks)?
- Edge cases covered?
- Integration tests where needed?
- All tests passing?

**Requirements:**
- All plan requirements met?
- Implementation matches spec?
- No scope creep?
- Breaking changes documented?

**Production Readiness:**
- Migration strategy (if schema changes)?
- Backward compatibility considered?
- Documentation complete?
- No obvious bugs?

**Security**
- SQL injection, XSS, auth/authz gaps, secrets in code, path traversal, CSRF, unsafe input, insecure crypto

**Correctness**
- Logic errors, off-by-one, race conditions, null dereferences, unhandled edge cases

**Performance**
- N+1 queries, missing indexes, memory leaks, blocking ops, excessive network calls

**Code quality**
- DRY violations, unclear naming, missing error handling, hard-coded values, tight coupling, functions >50 lines

**Best practices**
- Language idioms, framework conventions, type safety, null handling, test coverage

Only report real issues. Do not acknowledge good code, add compliments, or write a summary.
If there are no issues, say so in one line.

## Output Format

```markdown
### 🔴 Critical / 🟡 Medium / 🟢 Low — Short title (file:line)

What is wrong and why it matters. What needs to change.
```

Group by severity. One paragraph per issue — no more. No summary, no strengths, no resources section.

### Assessment

**Ready to merge?** [Yes/No/With fixes]
**Reasoning:** [Technical assessment in 1-2 sentences]
